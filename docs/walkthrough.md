# Как разобраться в проекте

Открой рядом [Scoring](http://localhost:3000/d/fraud-scoring) и этот файл. Не пытайся запомнить сразу названия всех контейнеров: сначала проследим один платёж.

## Шаг 1. Что мы вообще решаем

Представь поток платежей банковской карты. По каждому платежу нужно быстро сказать: насколько он подозрителен? Наша модель возвращает `score` от 0 до 1. Например, `0.83` — высокая оценка подозрительности. При пороге `0.5` такой платёж получает `fraud_flag=1`.

В этой учебной работе **не нужно доказывать качество модели**. Нужно сделать так, чтобы сервис непрерывно обрабатывал сообщения, а по графикам было понятно, работает ли он, успевает ли за потоком и какую модель использует.

Три разных вопроса:

1. **Сервис жив?** Есть ли новые результаты, не растут ли задержки и ошибки?
2. **Что модель насчитала?** Как распределены скоры, у каких сегментов больше флагов?
3. **Какая модель сейчас работает?** Загрузилась ли новая версия после обучения?

## Шаг 2. Откуда берётся «живой» поток

Файл `data/train.csv` сам по себе статичен. `transaction_simulator/app.py` превращает его в бесконечный поток: выбирает случайную строку, присваивает новый UUID, ставит текущее время и отправляет сообщение в Kafka. Между сообщениями по умолчанию 0.1 секунды — примерно 10 событий в секунду.

Пример сокращённого входа:

```json
{
  "transaction_id": "f8f5...",
  "data": {
    "amount": 120.0,
    "us_state": "CA",
    "merch": "some_store",
    "cat_id": "grocery_pos",
    "transaction_time": "2026-11-25 12:00",
    "emitted_at": "2026-11-25T12:00:01+00:00"
  }
}
```

В реальном сообщении есть и остальные признаки, нужные модели. UUID позволяет отличить два разных платежа, даже если они были сгенерированы из одной строки CSV.

**Посмотри сам:** Kafka UI → Topics → `transactions` → Messages. Там должны появляться новые события. Это не один прогон по CSV: процесс продолжает отправлять сообщения, пока контейнер работает.

## Шаг 3. Зачем между сервисами Kafka

Kafka — очередь с историей сообщений. Генератор пишет в топик `transactions`, скорер читает. Скорер пишет в `scoring`, writer читает.

Топик можно представить как журнал. **Offset** — позиция сообщения в журнале. **Consumer group** хранит, до какой позиции дошёл конкретный читатель.

Если writer временно остановлен, скорер продолжает складывать результаты в Kafka. Когда writer вернётся, он дочитает очередь. Прямой HTTP-запрос между этими сервисами потребовал бы отдельно придумывать хранение и повторную доставку.

Kafka не делает весь проект автоматически «без потерь»: нам всё равно нужно правильно подтверждать сообщения и обрабатывать повторы.

## Шаг 4. Что делает модель

`fraud_detector/src/preprocessing.py` превращает сырые поля в признаки: кодирует категории, извлекает время, считает расстояние клиент–мерчант, заполняет пропуски и преобразует числовые поля.

CatBoost получает подготовленную строку и возвращает вероятность. Затем сравниваем её с порогом:

```text
score = 0.83
threshold = 0.5
fraud_flag = 1
```

В `scorer.py` живут текущая модель, её preprocessing и версия. В `service.py` — цикл чтения Kafka, вызов модели и отправка результата.

Выход сохраняет ID и добавляет `score`, `fraud_flag`, `model_version`, время скоринга и поля для аналитики. `target` из CSV для принятия онлайн-решения не используется.

**Проверь:** Kafka UI → `scoring`. У результата тот же `transaction_id`, что у входного платежа.

## Шаг 5. Зачем отдельный writer и PostgreSQL

`scoring_writer/app.py` читает готовый результат и сохраняет его в `scores`. Скорер занимается моделью, writer — надёжной записью. Так задержки БД не смешиваются с задержками инференса.

Порядок записи:

```text
прочитал Kafka → INSERT в PostgreSQL → COMMIT БД → подтвердил offset Kafka
```

Что если БД уже сохранила строку, а writer выключился до подтверждения Kafka? После запуска Kafka отдаст сообщение повторно. У `transaction_id` есть уникальный индекс, а INSERT использует `ON CONFLICT DO NOTHING`, поэтому второй строки не будет.

Это **доставка как минимум один раз + идемпотентная запись**, а не магическое end-to-end exactly-once. Счётчик writer увеличивается только для новой реально закоммиченной строки. Счётчик скорера может включать повторные вычисления при повторной доставке.

**Посмотри:** Storage → таблица PostgreSQL по версиям модели. Это реальные строки, а не оценка их количества по метрикам.

## Шаг 6. Как сервисы рассказывают о себе

В сервисе есть маленький HTTP-сервер с `/metrics`. Там обычный текст:

```text
fraud_scored_total 1250.0
fraud_flagged_total 12.0
```

При обработке следующего сообщения код увеличивает соответствующие счётчики. Prometheus раз в секунду приходит и запоминает значения вместе с временем.

**Counter** — накопленный счётчик, обычно только растёт до рестарта процесса. Значение 1250 означает «1250 успешных результатов с запуска», а не «1250 в секунду».

**Gauge** — текущее значение, может увеличиваться и уменьшаться. Например, время последнего успешного результата или накопленная доля флагов.

**Histogram** — распределение наблюдений по границам. Например, сколько транзакций считалось быстрее 5 мс, 10 мс, 25 мс. На его основе можно оценить p95. Это приближение, точность зависит от границ бакетов.

Не путай два распределения: `fraud_processing_seconds` измеряет время, `fraud_score` — значения модели. Оба Histogram, но отвечают на разные вопросы.

## Шаг 7. Откуда в Grafana TPS и p95

Prometheus хранит значения, Grafana делает к нему запросы и рисует их.

```promql
rate(fraud_scored_total[30s])
```

Смысл: взять изменение счётчика за последние 30 секунд и оценить среднюю скорость в секунду. Поэтому TPS реагирует на остановку с небольшим сглаживанием, а не обрывается мгновенно.

```promql
histogram_quantile(0.95, sum by (le) (rate(fraud_processing_seconds_bucket[1m])))
```

Смысл: за последнюю минуту оценить время, быстрее которого обработались примерно 95% транзакций. Если p95 = 25 мс, около 5% были медленнее. Это не «все транзакции были по 25 мс».

Доля флагов за минуту — количество флагов за минуту, делённое на количество обработанных транзакций за ту же минуту. Мы не усредняем накопленный процент Gauge по времени: это дало бы другую величину.

## Шаг 8. Почему нужна ещё метрика возраста события

Допустим, модель обрабатывает платёж за 10 мс, но перед этим платёж минуту лежал в Kafka. График инференса выглядит хорошо, а пользователь получил результат слишком поздно.

`fraud_event_age_seconds` измеряет возраст от отправки генератором до получения результата скоринга. Сравни её p95 с p95 инференса:

- оба выросли — возможна перегрузка модели или CPU;
- возраст вырос, инференс прежний — стоит проверить очередь, поступление и потребление;
- TPS scorer нормальный, writer отстаёт — смотреть БД и writer.

Это подсказки для расследования, а не автоматическое доказательство причины. Для возраста нужны синхронизированные часы сервисов; на этом стенде они используют часы Docker-хоста.

## Шаг 9. Почему бизнес-графики идут из PostgreSQL

Prometheus хорошо хранит агрегаты: скорость, ошибки, задержки. Если создавать отдельную серию для каждого платежа или мерчанта, серий станет слишком много.

В PostgreSQL уже лежат отдельные результаты с `us_state`, `merch`, `cat_id`, суммой и версией. Поэтому Business делает SQL-запросы к БД через отдельного read-only пользователя.

Попробуй:

1. Выбери `CA` и оставь все мерчанты. Запомни число скоров.
2. Выбери одного мерчанта. Наблюдений станет меньше, распределение и TPS пересчитаются.
3. Верни All. Посмотри, почему у суммы подозрительных операций и доли флагов разная динамика: денежный размер платежей тоже имеет значение.

На графике плотности высота не равна вероятности одного бина. Высота умножается на ширину бина; сумма площадей равна 1. На графике `cat_id` доля считается по последним 1000 строкам всей системы, после чего выбирается сегмент — это отдельное скользящее окно, не диапазон сверху справа.

## Шаг 10. Как новая модель попадает в работающий сервис

Airflow — планировщик последовательностей задач. DAG описывает зависимости: сначала подготовить окно данных, потом train/test, preprocessing, обучение, проверка кандидата и публикация.

На выходе обучения недостаточно одного файла CatBoost. Нужны **модель + статистики preprocessing именно этой модели**. Иначе новый CatBoost может получить признаки в старой кодировке.

Публикация кладёт файлы в общий каталог, а затем атомарно переключает `latest.txt`. Скорер читает этот маленький указатель. При смене версии загружает оба объекта в память и только потом переключает рабочую пару. При ошибке остаётся старая версия.

На Scoring появляется оранжевая отметка загрузки, а в Storage — новая версия в результатах. Контейнер продолжает жить с прежним временем старта. Подробные команды — в README.

Проверка кандидата может запретить публикацию: обучение успешно, но новая модель хуже. Тогда сохранится отчёт кандидата, а действующая версия не изменится. Это нормальное поведение гейта.

## Шаг 11. Что такое алерт

График нужно смотреть глазами, алерт сам проверяет условие. В проекте есть два:

- давно нет новых результатов;
- необычно большая доля флагов модели при достаточном числе сообщений.

`Pending` означает «условие уже выполняется, но ждём подтверждения временем». `Firing` — условие продержалось достаточно долго. После восстановления алерт возвращается в нормальное состояние.

Запусти `python scripts/demo.py stall`. Скрипт остановит генератор, дождётся Firing, запустит его снова и проверит восстановление. На Scoring одновременно увидишь падение TPS и рост времени без успешного результата.

`high-fraud` — искусственная проверка другого алерта через порог решения, не через подмену истинной разметки. Она перезапускает скорер и оставляет тестовые флаги в БД, поэтому не используй этот интервал для вывода о качестве модели.

## Шаг 12. Как это показать на защите

За 5–7 минут:

1. Схема: вход → Kafka → модель → Kafka → БД; отдельно сбор метрик и обучение.
2. Scoring: TPS растёт, latency измеряется, распределение скоров меняется вместе с потоком.
3. Storage: записи идут, внизу число результатов и доля флагов по версии.
4. Host: CPU, RAM, сеть и диск Linux Docker-хоста.
5. Business: поменять оба фильтра, объяснить плотность и последние 1000 транзакций.
6. Airflow: запустить обучение; после одобренной публикации показать отметку и новую версию без рестарта.
7. Alerting: кратко остановить поток или показать сохранённые доказательства Firing → Normal.

Если можешь своими словами объяснить, почему счётчик не равен TPS, зачем writer подтверждает Kafka после БД и почему новая модель должна идти со своим preprocessing, ты уже понимаешь основную механику проекта.

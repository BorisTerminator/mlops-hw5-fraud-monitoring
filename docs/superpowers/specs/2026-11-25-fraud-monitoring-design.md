# HW-5: мониторинг потокового антифрода

Дата: 2026-11-25. Источник требований: Seminar_11._Domashnee_zadanie.docx.

## Задача
Отдельный воспроизводимый проект в MLOPS/HW-5: живой поток Kafka, CatBoost на CPU, запись в PostgreSQL, обновление модели без рестарта; поверх — Prometheus, Grafana, Node Exporter. Реализовать базовые и все дополнительные пункты задания на 8–10 баллов. Объяснения на русском в README и руководстве по демонстрации. Предыдущие HW не изменять.

## Подходы
1. Развить имеющийся HW-3 — выбранный исполнителем подход: уже есть рабочие контракты Kafka и переобучение Airflow, локальные данные и модель. Скопировать исходники без .git, runtime-артефактов и CSV, затем развивать в самостоятельном репозитории.
2. Основа с семинара — меньше работы, но чужие дашборды и Prometheus не засчитываются; архитектура уже есть у пользователя.
3. Переписать с нуля — лишний риск изменения контрактов без пользы для задания.

## Архитектура и контракты
transaction_simulator → Kafka transactions → fraud_detector → Kafka scoring → scoring_writer → PostgreSQL scores. Airflow переобучает CatBoost и атомарно публикует файлы и latest.txt в общем каталоге. Scorer загружает новую модель и препроцессор целиком, затем переключает рабочую версию; неудачная загрузка сохраняет предыдущую модель и регистрирует ошибку.
Вход: transaction_id, data. Выход сохраняет transaction_id, score, fraud_flag, model_version; добавляются us_state, merch, cat_id, amount и времена события/обработки для SQL-срезов. Сырые персональные поля не нужны для аналитики. Writer фиксирует Kafka offset после успешного commit в БД, transaction_id уникален для идемпотентной повторной доставки.

## Метрики
Scorer: обработанные сообщения, fraud count и доля, гистограмма latency на отдельной транзакции, гистограмма score, ошибки входа/инференса/публикации, время последнего успешного скоринга, end-to-end возраст события, число успешных загрузок с label version и время последней загрузки. Нельзя размечать метрики transaction_id/merch: это неограниченная кардинальность. Сегменты — SQL.
Writer: число реально вставленных строк после commit, гистограмма времени commit, fraud count, гистограмма записанного score, ошибки, время последней успешной записи. Повторная доставка не повышает счётчик записей.
Prometheus опрашивает scorer, writer и Node Exporter раз в секунду. Node Exporter показывает Linux-хост Docker Desktop (WSL2/VM), а не физическую Windows. В Linux — системный хост согласно bind mount.
Новая собственная метрика: возраст события при скоринге, позволяющий отличить быструю модель от накопившейся очереди; дополнительно ошибки и последний успешный скоринг. При сравнении с семинаром проверить, что хотя бы одна метрика отсутствует в примере.

## Grafana
Версионированные provisioning-файлы источников Prometheus/PostgreSQL, дашбордов и алертов. Доступ только localhost, параметры по умолчанию admin/admin для локального учебного стенда.
1. Scoring: TPS, p95 latency, fraud ratio, score heatmap, лаг события/ошибки; annotation смены модели по increase(counter{version}[30s]) с подписью версии. Версию показывать также в таблице истории загрузок.
2. Storage: TPS и latency записи, число fraud, score histogram, ошибки, число скоров и доля fraud по model_version из PostgreSQL.
3. Host: CPU, RAM, network, filesystem/disk I/O.
4. Business: SQL multi-select us_state и merch, распределение плотности score (нормированные бины), TPS по времени обработки с теми же фильтрами, fraud ratio по cat_id на глобально последних 1000 транзакциях (фильтрация после выбора последних 1000), дополнительный график суммы подозрительных транзакций / суммы оборота. Называть fraud_flag решением модели, а не подтверждённым мошенничеством. SQL-переменные экранировать через :sqlstring, datasource-пользователь только SELECT.

## Алерты и демонстрация
Два обязательных правила Grafana: остановка успешного скоринга >30 секунд (pending 15 секунд), доля решений fraud >20% в окне 1 минута при достаточном потоке (pending 20 секунд). Привязать правила к дашбордам. README содержит точные пороги, команды остановки/возобновления генератора и управляемую демонстрацию повышенного fraud через тестовый поток/порог с последующим восстановлением. Никаких внешних уведомлений не требуется.
Демонстрация публикации должна реально обучить и опубликовать новую модель, а не переименовать старый файл. Сохранить Airflow DAG; дать повторяемую команду и проверку model_version, метрик и отсутствия рестарта. При отклонении кандидата гейтом честно показывать это; отдельный явно обозначенный демонстрационный сценарий может обучать и публиковать модель для проверки мониторинга.

## Запуск и проверка
Самостоятельная compose-сеть и volumes, настраиваемые host-порты, не занимать инфраструктуру прошлых HW. CSV локально уже есть; для текущего запуска использовать копию/ссылку через .env (не публикуется). README для нового пользователя: откуда взять CSV, куда положить, docker compose up -d --build.
Проверки: meaningful unit/integration tests на метрики, сохранение контекста, idempotency writer, reload safety, SQL-фильтры; docker compose config; promtool check config; все Prometheus targets up; все provisioned дашборды и алерты через Grafana API; выполнить запросы каждой панели и проверить реальные непустые данные. Показать рост счётчиков за интервал, смену версии и firing/resolved минимум одного алерта. Локальная проверка графиков в браузере.

## Публикация

Пользователь запросил выполнение требований, включая публичный GitHub-репозиторий; публикация только после локальной проверки и согласования конкретного готового результата, если явной команды на публикацию к тому моменту нет.
